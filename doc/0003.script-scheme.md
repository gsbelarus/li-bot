When operators work manually with the browser, they follow a script. The script is a set of instructions that an operator follows to perform a task. The script is designed to be easy to follow and understand, and it is often used to train new operators.

Example of a script:

1. Find a Home link on the page and click it
2. Wait for the page to load
3. Move the mouse over the page
4. Find a link Proposed for you and click it
5. Wait for the page to load
6. Move the mouse over the page
7. Find a first contact and click it
8. Wait for the page to load
9. Move the mouse over the page
10. Scroll through the list of posts
11. Find a like button and click it

Our ultimate goal is to automate the execution of the script using Open Claw Bot.

Now concentrate only on the following task:

1. Create a structure to represent the script in a way that can be easily executed by the bot. This structure should include the instructions, the order of execution, delays, and any necessary parameters (e.g., selectors for finding elements on the page).
2. Create a DB schema to store the scripts in a database. This schema should include fields:
    - script name, 
    - description, 
    - script's plain text,
    - structured instructions.
    - disabled status.
3. Create a page in the control center to manage the scripts. This page should allow users to view a list of scripts in the database. Users should be able to create new scripts, edit existing ones, and delete scripts. The page should also allow users to enable or disable scripts.
4. Create a page in the control center to view the details of a script. This page should display the script's name, description, plain text, and structured instructions. Users should be able to edit the script's details on this page as well.
5. The structured instructions should be displayed as a JSON object on the script details page. This will allow users to easily understand the structure of the script and how it will be executed by the bot. Use <CodeMirror> to display the JSON object in a readable format.
6. The script's plain text should be displayed in a markdown format using <ReactMarkdown>. This will allow users to easily read and understand the script's instructions in a more human-friendly format.
7. User should be able to edit the script's plain text in markdown format. 
8. There should be a button to convert the script's plain text in markdown format to structured instructions in JSON format. Such conversion should be done using an OpenAI API function call. The API call should take the script's plain text as input and return the structured instructions as output. In the current implementation, the converted structured instructions are returned to the client and applied to the form state locally. They are persisted to the database only when the user explicitly clicks Save or Create.
9. For connecting to OpenAI API, use the following environment variables:
    - OPENAI_PROJECT_KEY
    - OPENAI_API_KEY
10. The OpenAI API calling should be done on the server side to keep the API keys secure. Create an API route in Next.js that will handle the conversion of the script's plain text to structured instructions. This API route should receive the script's plain text as input, call the OpenAI API to perform the conversion, and return the structured instructions as output. The client-side code should then call this API route when the user clicks the button to convert the script's plain text to structured instructions.

## Implemented database schema

The current code stores scripts in the MongoDB collection `scripts`.

### Collection: `scripts`

Document fields implemented in code:

- `_id`: ObjectId, Mongo primary key.
- `name`: string, required, trimmed.
- `description`: string, optional, defaults to empty string.
- `plainText`: string, required. This is the operator-authored markdown or plain step list.
- `structuredInstructions`: object, required. Stored as a flexible JSON object and initialized with an empty instruction structure.
- `isDisabled`: boolean, required, defaults to `false`.
- `createdBy`: string, required.
- `updatedBy`: string, required.
- `isDeleted`: boolean, required, defaults to `false`.
- `deletedAt`: datetime or `null`, defaults to `null`.
- `createdAt`: datetime, generated automatically by Mongoose timestamps.
- `updatedAt`: datetime, generated automatically by Mongoose timestamps.

### Indexes implemented in code

- `{ isDeleted: 1, name: 1 }`
- `{ isDeleted: 1, isDisabled: 1, updatedAt: -1 }`

### Notes about current implementation

- Deletion is implemented as soft delete through `isDeleted` and `deletedAt`.
- There is currently no uniqueness constraint on `name`.
- `structuredInstructions` is stored as `Schema.Types.Mixed`, so the application code is responsible for normalizing the JSON shape.
- `/api/scripts/convert` does not write to MongoDB. It only returns normalized structured instructions for the current form. Persistence happens later through the create or update script request when the user clicks Save or Create.

## Implemented JSON structure for `structuredInstructions`

The current code normalizes `structuredInstructions` into the following structure:

```json
{
    "version": 1,
    "summary": "Open the home page and like the first post",
    "defaultDelayMs": 1000,
    "steps": [
        {
            "order": 1,
            "kind": "click",
            "instruction": "Find a Home link on the page and click it",
            "delayAfterMs": 1000,
            "timeoutMs": 10000,
            "target": {
                "description": "Home navigation link",
                "selectors": [
                    "a[href='/feed/']",
                    "nav a[data-test='home-link']"
                ],
                "text": "Home",
                "role": "link"
            },
            "params": {}
        }
    ]
}
```

### Top-level fields

- `version`: currently fixed to `1`.
- `summary`: string summary of the script.
- `defaultDelayMs`: number, default delay between steps.
- `steps`: array of ordered step objects.

### Step fields

Each item in `steps` has the following fields:

- `order`: number, execution order.
- `kind`: string enum describing the operation type.
- `instruction`: string, human-readable instruction for the step.
- `delayAfterMs`: number, delay after the step completes.
- `timeoutMs`: number, timeout for the step.
- `target`: object or `null`, describing the intended DOM target.
- `params`: object with scalar values only.

### `target` fields

When present, `target` has the following fields:

- `description`: string.
- `selectors`: array of strings.
- `text`: string.
- `role`: string.

### Supported `kind` values in current code

- `navigate`
- `click`
- `hover`
- `wait`
- `wait_for_page`
- `move_mouse`
- `scroll`
- `type`
- `press_key`
- `extract_text`
- `assert_visible`
- `custom`

### Rules enforced by current normalization code

- If `structuredInstructions` is missing or malformed, it is normalized into a safe default object.
- `version` is always rewritten to `1`.
- `steps` defaults to an empty array.
- Invalid `kind` values are converted to `custom`.
- `delayAfterMs` defaults to `0` for `navigate`, `wait`, and `wait_for_page` when missing or invalid.
- `delayAfterMs` defaults to `1000` for the other action kinds when missing or invalid.
- `timeoutMs` defaults to `10000` when missing or invalid.
- `params` only keeps scalar values: `string`, `number`, `boolean`, or `null`.
- `target` becomes `null` when it is missing or not an object.

### Execution parameter conventions used by the current interpreter

The current runtime in `rc` supports a few important scalar `params` conventions in addition to the generic schema above:

- `navigate`
    - `url`: absolute URL to open in the current attached tab.
- `wait`
    - `durationMs`: fixed dwell time.
    - `minDelayMs`: minimum dwell time for random waits.
    - `maxDelayMs`: maximum dwell time for random waits.
    - `moveMouse`: boolean flag to simulate mouse movement during the wait.
    - `moveMouseCount`: optional number of mouse-movement bursts during the wait.
- `wait_for_page`
    - `readyState`: expected document readiness, usually `complete`.
    - `urlIncludes`: substring that must appear in the URL.
    - `urlEquals`: exact URL match.
- Repeated elements or section-scoped actions
    - `containerSelector`: CSS selector for the section or repeated container to search within.
    - `containerText`: visible text that identifies the section to search within.
    - `containerIndex`: 1-based index for the matching container.
    - `index`: 1-based index for the matching target element inside the selected scope.

These conventions are especially useful for scripts such as:

- navigate directly to a known page,
- dwell on a page for a random human-like interval,
- click the first matching profile inside a named section,
- click the More button inside the third post,
- click the Like button inside the same repeated post container.
